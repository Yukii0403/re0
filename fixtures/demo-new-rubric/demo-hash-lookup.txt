计算机专业实验报告：哈希索引与顺序扫描的查询性能比较
（演示用合成学生报告；不是实际学生作业）

一、实验目标
比较在不同记录规模下，顺序扫描与哈希索引查询一个已存在键的耗时，并讨论结果能否支持理论复杂度判断。

二、环境与方法
实验使用 Node.js 20，在一台 8 核笔记本电脑上运行。每条记录由整数键和短字符串值组成。先按键从 0 到 N-1 生成 N 条记录；顺序扫描从数组开头逐条比较键，哈希索引使用 Map.get。查询键固定为 N-1，因此顺序扫描需要访问最后一条记录。三个规模分别为 1,000、10,000 和 100,000 条。代码使用 performance.now() 记录一次查询的开始和结束时间，再换算为毫秒。

关键伪代码：
function scan(rows, target) {
  for (const row of rows) if (row.key === target) return row.value;
}
function indexed(map, target) { return map.get(target); }

三、实验结果
记录数 N       顺序扫描耗时(ms)    哈希查询耗时(ms)
1,000          0.02                0.01
10,000         0.21                0.02
100,000        2.16                0.03

在 N=100,000 时，顺序扫描耗时 2.16 ms，哈希查询耗时 0.03 ms。因此哈希查询的加速比为 2.16 / 0.03 = 7.2 倍。表中顺序扫描耗时随 N 增大而上升，而哈希查询变化较小，这与本实验的预期一致。

四、分析与局限
由于 Map.get 的平均时间复杂度为 O(1)，本实验已经证明哈希查询在任何数据规模和任何输入分布下都恒定耗时。顺序扫描最坏情况下为 O(N)，因此哈希方案在这三组测试中更快。

本次只记录每个规模的一次查询，没有报告重复运行次数、预热方案或耗时离散程度。构建 Map 的时间与额外内存没有计入结果；哈希冲突以及未命中键的查询也没有单独测试。因此这些数据主要反映本机、末尾命中场景下的单次查询，不能直接代表整个系统的吞吐量。

五、结论
在给定样本和末尾命中条件下，表格支持哈希索引查询更快的观察。后续应加入重复试验、不同键位置、未命中查询、构建成本与内存占用，再判断整体方案是否更优。
