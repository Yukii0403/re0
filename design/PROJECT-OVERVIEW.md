# AutoGrader 项目技术总览（比赛版）

本文供评委和首次阅读仓库的开发者快速理解**完整设计、技术实现、工程完整性与创新性**。它描述截至 2026-09-26 的比赛原型，不把设计目标、单例演示或结构校验当作总体效果证明。各层的历史决策和详细契约见文末链接；早期自动给分评估计划不代表当前交付方向。

**团队：**游龙队 · 毛远哲（深圳大学，计算机科学与技术）· 沈琪峰（暨南大学，数学与应用数学）。**入口：**[实时分析](https://autograder-sotv.onrender.com/realtime/) · [三案例演示](https://autograder-sotv.onrender.com/) · [GitHub 仓库](https://github.com/Yukii0403/re0)。

## 1. 完整设计：AI 辅助判断，教师保留评分权

**场景。** 计算机实验报告往往既有文字论证，也有数值、表格、代码和公式。教师需要通读报告形成整体判断，再按 rubric 回到具体原文核查。AutoGrader 的目标是把值得优先核查的质量观察和出处先呈现出来，而不是代替教师决定精确分数。

**权威边界。** 学生原件和教师上传的 rubric 是只读来源；检索计划、证据候选、验证结果及模型评价都是派生工作物。原始 rubric 的条目及分值不因检索或模型判断而被改写。模型可以提出定性观察，教师可以确认、修改或否定，并自行给分；整体评语是教师复核后的草稿，不自动发布。

```text
学生原件 ──→ L1 原文与 Source Index ────────────────┐
教师 rubric ─→ 原始条目及哈希 ─→ 检索计划 ──────────┤
                                                ↓
                    L2 证据聚焦（候选，不是结论）
                         ↓             ↘ 完整原文 / 原始资产始终可用
                    L3 按需机械验证
                         ↓
                    L4 逐 rubric 条目的定性评价
                         ↓
              来源 / 契约 / 覆盖校验 → 教师核对与给分
                                              ↓
                               整体评语草稿（待教师批准）
```

| 环节 | 承担的责任 | 不承担的责任 |
| --- | --- | --- |
| **L1 Source Index** | 从有文本层的 PDF、DOCX 或 TXT 建立原文顺序、偏移和可用的页/位置引用；原始图像、公式按资产引用供下游查看 | 不由 LLM 改写正文，不在此层转写 LaTeX 或解释图像 |
| **L2 Evidence Focus** | 在 rubric 条件下高召回定位候选片段/资产，并记录检索覆盖与不确定状态 | 不把“未检索到”当作“学生没写”，不以候选集合替代全文，不评分 |
| **L3 Verification** | 对适合确定性规则的问题调用受限工具，例如数值重算、单位、编号及内部一致性；给出 `pass / fail / unverified` 和来源 | 不自动裁决语义质量；图表外观等视觉判断不伪装成机械结论；检查是按需的，不要求每条 rubric 都有结果 |
| **L4 Assessment** | 回到**原始 rubric 的可评分条目**，结合完整原文、候选和验证结果提出有定位的优点、问题、缺项；必要时标待审 | 检索面不是评分原子；模型不提交最终分数，L3 `fail` 也不自动扣成某个分数 |
| **教师与评语** | 教师核查原文、确认/修改评价并给精确分；系统据已确认内容和教师给分生成整体评语草稿 | 未确认内容不应冒充教师意见；草稿未经批准不交付学生 |

“L5 校验”在当前比赛版不是另一个让模型评分的环节，而是贯穿各层的 **schema、哈希、引用、覆盖与教师发布闸**。第一屏的 Top N 是**上限而非配额**：只让相关、可核查、值得优先看的观察上屏；依据不足的重大疑点进入待核查区，而非包装成确定结论。

## 2. 技术实现：来源绑定的分层流水线

运行环境为 Node.js **22+**，服务端用 Docker 部署。PDF 文本抽取、页面图渲染和 DOCX 解包所用依赖记录在 [`package.json`](../package.json)；模型端点和密钥通过服务端环境变量配置，不写入仓库。公网演示同时提供实时分析入口和三个预生成案例，两者性质不同。

**输入和契约。** 教师 rubric 先形成规范化条目，并保留原件哈希；检索计划只是可修订的工作物。L1 输出原文文本与索引：索引项的字符偏移应能切回抽取后的原文，文档身份绑定学生上传**原件**的哈希。需要区分：这证明索引没有改写其抽取文本，**不证明 PDF 文本层或视觉内容被完美抽取**。L2 保存候选的 `source_ref`、偏移、原文引文及检索诊断。L3 的操作数由程序从所指原文解析，模型不能只提交一个无出处的数字；无法确定对象、量纲或计算前提时保留 `unverified`。L4 保存逐条评价、引用与送审原因，供教师界面使用。

关键数据契约分别在 [原文索引](document-index.schema.json)、[规范化 rubric](canonical-rubric.schema.json)、[检索计划](retrieval-plan.schema.json)、[候选证据](evidence-candidates.schema.json)、[验证结果](verification-checks.schema.json)、[定性评价](rubric-assessment.schema.json)和[整体评语](summary.schema.json)。原始 rubric、执行 profile、学生原件和派生产物通过身份与哈希校验关联；输入改变时，旧产物不能被当成新报告的结果沿用。

**教师界面与服务。** 实时站可上传新 `.txt`/`.pdf` 报告，或上传有明确编号和整数分值的 UTF-8 TXT rubric；新 rubric 先预览确认。任务在服务端运行，完成后进入教师视图。PDF 的“查看原文”在新标签打开原 PDF 的对应**页**，浏览器负责缩放；这不是逐字高亮。TXT 则回到原始文本位置。教师下载工作表发生在浏览器端。预置案例网页是已生成结果，打开它不会触发新的模型分析。

## 3. 工程完整性：已交付什么，验证到哪一步

| 工程面 | 仓库中可核查的交付 | 尚不能推出的结论 |
| --- | --- | --- |
| **可运行性** | [`README`](../README.md)给出 Node 22+ 本地启动；[`Dockerfile`](../Dockerfile)与[`render.yaml`](../render.yaml)提供公网服务部署配置；实时站和预置站有独立入口 | Render 免费实例稳定性、PDF 每次都能在小内存实例跑完 |
| **契约与失败处理** | 各层 JSON Schema、来源偏移/原件哈希、教师给分输入校验；端到端入口能对账条目集合并在层失败时停止下游 | 格式与来源校验不等于模型解释在语义上正确 |
| **测试与示例** | `npm run selftest` 对应离线自测入口；仓库带三份预生成案例及来源清单；[演示脚本](../delivery/demo-3min.md)记录一份全新**合成**报告 + 新 rubric 的公网真实模型全链运行 | 单个案例不能给出总体准确率、平均耗时或教师节时结论 |
| **公开服务边界** | 上传大小、单实例配额、按任务产物访问与有限保存期；密钥留在服务端；教师导出在浏览器本地完成 | 当前没有教师账户、长期保存、跨实例可靠额度控制或生产级数据治理 |

复现时需特别注意：仓库**不包含**模型密钥、用户上传件、完整原始数据集和部分原始报告；可运行代码、自测与浏览预置产物，不能仅靠克隆仓库重算全部历史实验。预置 PDF/数据集案例包含第三方材料，其再分发权限需要单独核实；本项目的 [MIT 许可证](../LICENSE)不覆盖这些材料。

**效果验证边界。** 目前可以说“存在可交互的教师核对原型”和“至少有记录在案的新材料真实模型闭环”；不能说“已证明教师节省多少时间”或“定性评价达到某个普遍准确率”。原文锚定率、测试通过和模型与分数的相关性分别衡量不同问题，不能互相替代。真实教师复核的正确性与耗时仍待后续测试。

## 4. 创新性：可说明的设计贡献，而非未经验证的领先性

1. **来源与解释分权。** 将确定性 Source Index 与模型派生判断隔离：原文可回切、原件可寻址，模型不能把自己的转写覆盖来源。这是可审计的系统边界，不声称发明了新的 PDF 解析算法。
2. **证据聚焦但不截断判断材料。** Rubric 检索面只引导注意力；L4 仍可查看完整原文。“检索没找到”和“全文确认没有”严格区分，避免把召回漏检直接变成对学生的负面判断。
3. **有限验证与诚实弃权。** LLM 决定要核查什么，固定工具从绑定来源解析数值并复算；对象、单位或前提不清时返回 `unverified`。这比让模型自由写程序或自由给一个数字更容易审计，但**尚无消融结果证明它提升了总体评价准确率**。
4. **以教师阅读路径组织输出。** 少量优先观察、缺项待核查、原文跳转、教师确认/改写/给分、整体评语草稿组成闭环；模型擅长提出有依据的定性观察，精确评分权留给教师。这里的创新主要是**面向任务的组合与权责设计**，不是宣称模型本身或自动评分算法达到新的研究水平。

上述四点是**设计贡献**；“创新性带来准确率或效率增益”仍需要对照组、独立样本与教师使用研究验证。比赛演示应区分“已实现”“在个别样例中观察到”和“尚未验证”。

## 5. 未来优化方向（均未在比赛版实现）

以下是后续研究与产品路线，**不是当前线上站点的功能承诺**：

1. **批量作业上传与任务队列。** 支持同一课程、同一 rubric 版本下多份报告批量提交；为每份作业独立记录原件哈希、运行状态、成本、失败与重试，避免交叉引用或重复计费。先验证单份结果稳定性，再扩展并发与批处理。
2. **全班整体分析。** 在教师完成必要复核后，汇总各 rubric 维度常见优点、缺项和逻辑问题，提供可回到具体作业的班级级诊断。聚合应区分“模型初判”和“教师确认”，保护学生隐私，不能把机器候选直接当成班级事实或自动排名。
3. **L3 的受控程序生成验证。** 探索让 LLM 针对固定工具目录覆盖不到的计算提出短程序，但必须在无网络、最小权限、限时限内存的隔离环境中运行；输入值仍由系统绑定原文，保存程序、输入、输出和版本以便复算。未通过来源校验、沙箱或教师复核时只能返回 `unverified`，不能将生成程序的输出直接当作评分依据。现行 L3 仍只使用预先定义的有限工具。
4. **更广的文档与效果验证。** 逐步改善复杂表格、双栏与视觉资产的处理，并用新的独立报告及真实教师复核测试评价准确性和阅读时间。只有这些验证完成后，才讨论效率提升的量化结论。
